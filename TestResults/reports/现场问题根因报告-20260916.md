## ① 点击历史记录弹出「System.Windows.Documents.Run 不是 Visual 或 Visual3D」

**判定**：✅ 根因确凿，已修复。

### 证据链

1. 报错来自全局异常兜底（`App.xaml.cs` 的 `DispatcherUnhandledException`，把异常消息直接弹给用户）：
   用户看到的文案与 .NET 对该异常的中文消息一字不差。
2. 命中测试实测（`BugRepro history-run`，真 `MainPage` + 真 `ListView`）：

   ```
   时间戳列里的显式 <Run> 数量: 6
   时间戳文字的命中结果类型: System.Windows.Documents.Run

   ===== 复现成功 =====
   异常: System.InvalidOperationException
   消息: “System.Windows.Documents.Run”不是 Visual 或 Visual3D。
      at MS.Internal.Media.VisualTreeUtils.AsVisual(...)
      at System.Windows.Media.VisualTreeHelper.GetParent(DependencyObject reference)
   ```
3. 触发点在 `ClassNote/Views/MainPage.xaml.cs:184`
   （`SessionList_MouseDoubleClick` 里的 `FindVisualParent<CheckBox>(src)`），
   而 `FindVisualParent` 一路调用 `VisualTreeHelper.GetParent`。
4. **版本回归点已用 git 证实**：`0.3.4` 的时间戳是
   `<TextBlock Text="{Binding StartTime, StringFormat=...}" />`（命中结果是 TextBlock，`TextBlock` 是 Visual，不抛）；
   `0.4.2` 之后为显示"周几"改成了
   `<TextBlock><Run .../><Run .../></TextBlock>`（见 `git show e3685b2:ClassNote/Views/MainPage.xaml` 与当前 `MainPage.xaml:270-275`）。
   **代码一行没变，坏的是它脚下的元素类型。**

### 根因

`Run` 是 `FrameworkContentElement`（**不是 Visual**）。凡是从 `e.OriginalSource`（命中测试可能给出行内元素）
向上遍历的代码，都必须分派到"内容树的父级查询"API，而不能无条件用 `VisualTreeHelper.GetParent`。
`Controls/SmoothScroll.cs:101` 早就写对了这个分派，`MainPage` 这一处漏了。

### 修复

- 新增 `ClassNote/Controls/VisualTreeWalk.cs`：统一的分派实现（Visual/Visual3D → `VisualTreeHelper.GetParent`；
  `ContentElement` → `ContentOperations.GetParent`；`FrameworkContentElement` → `Parent`），并提供
  `FindAncestor<T>`；**永不抛异常**。
- `MainPage.FindVisualParent` 改为委托给它。
- 回归测试 `ClassNote.Tests/Views/HistoryListHitTestTests.cs`：用真 `MainPage` 做命中测试，断言
  (a) 命中结果确实是 `Run`、(b) 裸用 `VisualTreeHelper.GetParent` 会抛用户看到的那句、
  (c) 修复后的走法能找到 `ListViewItem`/`ListView` 且全程不抛。

## ② 升级到 1.0.1 后反复卡死，必须重启进程

**判定**：✅ 找到并修复一处**可实测的 UI 线程硬阻塞**（本次事故的主嫌）；
⚠️ 另保留一处"未完全排除"的可能，已加字段诊断（见 §6）。

### 证据链（实测数字，非估算）

复现器 `BugRepro ui-block` 直接驱动生产代码
`IncrementalTranscriptionSession`（真类、真工作线程、真 30 秒分块路径，只把 241MB 模型推理换成固定耗时）：

| 音轨数 | 单块推理 | UI 线程同步收尾耗时 | 收尾期间 `DispatcherTimer` 最大间隔 |
|---|---|---|---|
| 1（仅麦克风） | 5.0 s | **2003 ms** | 2011 ms |
| 2（麦克风 + 系统声音，默认配置） | 5.0 s | **4012 ms** | 4021 ms |

**修复后同参数复测**：

| 音轨数 | UI 线程同步收尾耗时 | 收尾期间 `DispatcherTimer` 最大间隔 |
|---|---|---|
| 1 | **0 ms** | 112 ms |
| 2 | **0 ms** | 113 ms |

### 根因（代码路径逐帧）

```
用户点「结束录音」
  → RecordingPage.StopRecordingAsync()            (UI 线程)
  → RecordingViewModel.StopRecordingAsync() → StopCapture()   (快，毫秒级)
  → RecordingEnded 事件 → MainWindow.NavigateToMainPage()
  → 旧页面 Unloaded → RecordingPage.Page_Unloaded()            (UI 线程)
  → RecordingViewModel.Dispose()
  → IncrementalTranscriptionSession.Dispose()
  → foreach (worker) worker.WaitForCompletion(2000)   ← 每路固定等满 2 秒（IncrementalTranscription.cs）
```

- 这个等待是 **2 秒/路 的固定开销**（`WaitForCompletion(2000)` 是**上界**，不是"最多等到干完"），
  与尾部补算是否早就完成无关；两路来源（`RecordingSettings` 的默认档）就是 **4 秒**。
- 而它**本来就是多余的**：尾部补算由课后管线负责，`NoteProcessor.ProcessAsync` 里已有
  `incremental.WaitForCompletion(TimeSpan.FromSeconds(120))`——在**后台线程、2 分钟预算**下等才是正确等法。

### 为什么表现是"卡死、必须重启"

1. 结束录音时界面**整整 4 秒不响应**（点击、触摸、滚动全部排队），且每次停录都发生 → 用户印象为"反复卡死"；
2. 这 4 秒里 UI 线程上**所有 `DispatcherTimer` 一律停摆**——课表调度器（`MainWindow._schedulerTimer`）与
   `RecordingPage` 的"到点自动下课"看门狗（`StartAutoStopWatcher`）都在其中；
3. 主嫌之外还叠加了内存/磁盘压力（600MB STT 模型 + 双路 WAV + 每 10 秒 4K 全屏截图），
   而 `App` 的全局异常兜底会把异常吞掉（`e.Handled = true`），用户拿不到任何线索，只能杀进程。

### 修复

1. `IncrementalTranscriptionSession.Dispose()`：删掉逐路 `WaitForCompletion(2000)`，
   **只做标记 + `SignalInputComplete()`，立即返回**（工作线程自行处理完尾部后退出；课后管线照旧会等它）。
2. `RecordingPage.Page_Unloaded()`：把 `_viewModel.Dispose()`（还包含音频设备 `Dispose` 的 Join）
   整体移到后台线程；`DispatcherTimer` 必须在自己的线程上停，故先把 `_elapsedTimer` 用新暴露的
   `RecordingViewModel.StopElapsedTimer()` 停掉再移交。
3. 新增 `ClassNote/Services/UiWatchdog.cs`：UI 线程 500ms 心跳，任一次间隔 ≥2 秒就写
   `classnote-crash.log`（含当时阶段），把"卡了多久/在干什么"变成可查证据。
4. 回归测试 `ClassNote.Tests/Services/IncrementalTranscriptionDisposeTests.cs`：
   在"工作线程正跑 5 秒慢推理"时断言 `Dispose()` < 500ms 返回，并断言工作线程随后仍能自行收尾退出
   （**不是**靠杀线程）。

## ③ 多媒体（触摸屏）长按无法替代鼠标右键

**判定**：✅ 能力缺失（不是 bug），已补齐。

### 证据链

- 全仓检索 `Stylus` / `Touch` / `TouchDown` / `LongPress` / `Holding` / `Manipulation`：
  **生产代码 0 处命中**（只有文档与 MathJax 资产）。
- 也就是说，右键菜单（查看笔记 / 导出 PDF / 删除，`MainPage.xaml` 的 `SessionContextMenu`）
  只依赖 `ContextMenuOpening` —— 而 WPF 在 Windows 10 **桌面模式**下不会把触摸"按住不放"翻译成鼠标右键
  （系统的"按住以右键单击"只在平板模式的触摸外壳里生效）。
  一体机上没有鼠标 = **这三个功能没有任何入口**。
- 顺带实测（`BugRepro context-menu`）：右键/长按落点命中到时间戳 `Run` 时，
  `AttachSessionToContextMenu` 仍能正确挂上该行记录（走 `ItemsControl.ContainerFromElement`，不受 Visual 限制），
  所以菜单本身没问题，缺的就是"怎么唤出来"。

### 修复

- 新增 `ClassNote/Controls/TouchLongPress.cs`：附加行为，按下后 **550 ms** 内未抬起且位移 < 14 px
  即把该元素的 `ContextMenu` 就地打开；只认触摸/触笔（不干扰真鼠标右键）；移动即取消（不影响滚动）；
  不吞事件；触摸与触笔事件自动去重。
- 接入：`App.xaml` 的 `ListViewItem` 样式挂 `controls:TouchLongPress.IsEnabled="True"`。
- 右键菜单项高度 `34px → 44px`（微软触控建议值，原高度手指常点滑到相邻项）。
- 设置项「触摸屏优化」（`AppSettings.TouchOptimizations`，默认开）可在设置窗口关闭，
  关闭后长按不再生效（文案里已写明"没有鼠标就再也调不出右键菜单"的代价）。
- 回归测试：断言 `App.xaml` 的样式确实挂上了长按行为与 `PanningMode`（防止"只写了类没接线"）。

## ④ 语文课记录在上节物理课上，且物理课记录丢失（相差 1 小时）

**判定**：✅ 根因确凿，已修复。

### 证据链

1. 课表：物理 09:00–09:45、语文 10:00–10:45。用户现场：物理那节**没能按时自动结束**，语文整节**没有记录**。
2. 复现器 `BugRepro schedule-handoff`（用生产 `ScheduleEngine` + `MainWindow` 的真实判定顺序）：

   ```
   09:00 触发: [物理]          ← 物理那节开始录音
   10:00 触发: [语文]          ← 语文到点，引擎照常返回待触发
     跳过「语文」：到点自动开始时正在录音（物理那节还没停）
   此时仍在录音的会话课程 = 物理
   新开始的会话 = []

   ===== 复现成功：一节录音跨了两节课 =====
   ```
3. 触发点 `MainWindow.xaml.cs` 原实现：
   ```csharp
   if (IsRecordingActive) { ShowTrayBalloonIfHidden("定时记录已跳过", ...); return; }
   ```
   —— 整节跳过且**不重试**；再加上 `ScheduleEngine.Evaluate` 把该条目写进"当天已触发"记忆
   （`_firedOn[entry.Id] = today`），这一节当天**再也不会被录**。
4. **上游触发条件正是问题②**："到点自动下课"是 `DispatcherTimer` 看门狗，问题② 的 4 秒 UI 阻塞
   会把它推迟；持续繁忙/长阻塞时完全不触发 → 录音跨进下一节课。

### 根因

课表允许一节课接一节课，但代码对"上一节还没停"只做**整节丢弃**，没有"先收尾上一节再开始这一节"的路径。
后果：语文课的内容全录进了那条仍标着"物理"的会话（**看起来物理有记录**），
课表上的语文那一节永远空白 —— 用户表述为"语文课记录在上节物理课上且物理课记录丢失"。

### 修复

- `MainWindow.StartScheduledRecordingAsync`：到点时若仍在录音，**先结束上一节**（走
  `RecordingPage.RequestStopAsync()`，与"结束录音"按钮、自动下课看门狗同一条收尾路径），
  成功后再正常创建本节会话；只有"确实停不下来"才放弃本次（20 秒上限），且**不再把这一节从当天划掉**，
  交给下一个 10 秒调度周期重试。
- 决定逻辑抽成纯函数 `Services/ScheduledRecordingHandoff.cs`，由
  `ClassNote.Tests/Services/ScheduledRecordingHandoffTests.cs` 锁住四个分支
  （含"正在录音却仍然开始新录音"这条致命分支的守卫）。
- 回归测试同时守住"一天里同一节课只触发一次"，避免修复退化成"每 10 秒重开一节课"。

## ⑤ 触控支持非常差

**判定**：✅ 能力缺失，已补齐主要成因。

### 证据链

- 全仓检索 `PanningMode` / `IsManipulationEnabled` / `Stylus`：**0 处**。
  WPF `ScrollViewer.PanningMode` 默认是 `None` → **手指拖动列表不会滚动**，只能去够那根滚动条；
- 滚动条模板写死 `ScrollBar Width="9"`（`App.xaml`），触摸下几乎按不住；
- 列表行 `MinHeight=46` 尚可，但右键菜单项只有 `34px`；
- 长按无右键（见问题③），等于触摸下**没有**任何"次要操作"入口。

### 修复

| 项 | 改动 |
|---|---|
| 单指拖动滚动 | `ListView` 样式设 `ScrollViewer.PanningMode=VerticalOnly` + `PanningDeceleration` |
| 滚动条 | `9px → 16px`（拇指滑块视觉仍为细条，命中区变大） |
| 菜单项高度 | `34px → 44px` |
| 长按右键 | 见问题③（`TouchLongPress`） |
| 列表行高 | `46 → 52`（提高触摸命中率） |
