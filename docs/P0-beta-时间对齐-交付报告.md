# P0-β 交付报告：截图按时间戳归属分段（两源可互证的前提）

> 对应方案 `docs/方案-化学笔记质量修复.md` 的 **P0-β**。
> 承接 `docs/P0-alpha-OCR规范化-交付报告.md`（P0-α 已交付）。

## 1. 为什么要做这一步

方案的立论是"转写是同一节课的高置信词典，可用来校正课件 OCR，并区分'老师讲的结论'与'课件/试卷上的字'"。
但在这之前，**代码结构上这件事根本做不到**：

- 课件截图带的是**绝对秒**（`screenshots.timestamp`，`Screenshot.cs:7`）；
- 分段用的是**字符偏移**（`NoteSegmenter` 的 `NoteSegment.Windows`）；
- 两者之间没有任何桥梁。

于是 `NoteSegmenter` 只能把 OCR 条目**按序号均摊**到各段（原注释写得很清楚：
"与时间对齐解耦，避免'转写很短而 PPT 很多'时按时间切分把大量 OCR 重复塞进每一段"）。
后果是：**第 N 段里放的是别的时间段的幻灯片**，同一段内转写与截图讲的根本不是同一时刻的事。
两源因此无法互证——P1 的交叉核验在结构上就无从谈起。

| 产物 | 位置 | 作用 |

## 3. 关键设计决策

### 3.1 用"块反查"而不是"字符比例缩放"

最省事的做法是"按转写总长把时间等比摊到字符上"。它便宜，但**会在真实素材上系统性偏移**：
一节课里"老师讲了很久但没说话"（做题、看视频）与"话很密"的时间段字符密度差好几倍，
等比缩放会把后半节课的截图错位到最后几分钟。

因此本实现改用**块反查**：转写是由 30 秒一块拼出来的（`TranscriptionChunking.FramesPerChunk = 3000` 帧 = 480000 采样 = 30 秒），
库里逐块存着文本。于是"第几个字符属于哪一块"是**可精确推算**的，时间区间由块号推出。

块号到起始秒直接按 `index * 30` 算，**刻意不依赖 `transcript_chunks.start_seconds` 字段**：
块号本身就是"这段音频在第几个 30 秒"的硬语义，而字段对"丢过的块"没有约束。

### 3.2 对不上就放弃，绝不编数据

`TranscriptTimeline.Build` 会校验"块文本总长 == 实际文本长度"。不等就返回 `null`——
那种情况下文本是以别的方式拼出来的（缺块、换过实现），任何按字符推断时间的行为都是在编数据。

`BuildForSession` 里读库失败同样返回 `null`（有专门的测试用替身验证这条：
`BuildForSession_ReturnsNullWhenRepositoryThrows`）。**时间对齐只是"更好"，绝不能成为"跑不起来"的原因。**

### 3.3 容量回填：截图在时间上会成簇

老师连续翻页时，3 张截图挤在 15 秒里，而转写按字符均匀分成 3 段——直接按时间分配会把它们
**全压进第 1 段**，撑破那一段的输入上限（`DefaultMaxCharsPerSegment = 6000`）。

因此分配后加一道**容量回填**：单段超过单段上限的 60% 就不再收，剩下的按"剩余容量最多"的段依次放。
用单段上限而不是"平均值"做阈值是刻意的：平均值会被段数摊薄，段数一多就没人愿意收留大截图。

测试 `AssignOcr_ReflowsScreenshotsThatWouldOverflowOneSegment` 用 3×4000 字锁住了这条：
一张不丢，且没有任何一段超过单段上限。

### 3.4 录音结束后截的图不丢

时间超出所有段的截图（下课铃响后又截了一张）归入最后一节有时间区间的段，
由 `AssignOcr_KeepsScreenshotsTakenAfterTheLastSegment` 锁定。

## 4. 实测结果

```
dotnet test ClassNote.Tests\ClassNote.Tests.csproj
已通过: 504 / 失败: 0 / 总计: 504
```

（P0-α 结束时为 495；本次新增 9 个时间轴测试，**修改了 0 个既有断言**。）

验收标准（方案里定的"抽查 5 段：段内截图时间戳必须落在该段转写时间范围内"）由
`AssignOcr_PutsEachScreenshotIntoTheSegmentThatCoversItsTime` 以确定性方式覆盖：
给定"每 100 字 = 30 秒"的时间轴，5 秒的截图落第 1 段、95 秒落第 2 段、125 秒落第 3 段。

**回归检查**：全部既有的 `NoteSegmenter` 测试仍然通过——它们的 `timeline` 参数默认为 `null`，
走的是与改动前**逐字相同**的均摊路径（`AssignOcr_WithoutTimeline_FallsBackToRoundRobin` 显式锁定）。

## 5. 一处如实申报的测试噪声

本轮全量测试中出现过一次 `IncrementalTranscriptionDisposeTests.Dispose_IsIdempotent_AndSignalsInputComplete`
失败（"工作线程应当在处理完尾部后退出"）。**单独重跑该测试类与全量重跑均通过**，
且该测试与本次改动无任何交集（它验证的是增量转写线程的退出时机，不经过分段器）。
判断为既有的计时脆弱用例：它在满负载跑整套测试时超时，属预先存在的问题，
本次不动它，但记在这里以免下次误判为新增回归。

## 6. 下一步（P1）

时间对齐就位后，P1 的两件事才有依据可做：

1. **提示词分级**：公式/化学式/数值/术语"以转写为准按正确写法输出"，叙述性内容允许概括合并；
2. **证据标签**：同一段里"转写里说过 / 只在课件上 / 两源冲突"三态标注，把试卷原题与老师的结论分开；
3. **`NoteQualityGuard`**：核对标注覆盖率、重复率、危险断言（例如化学里的"可用泡沫灭火器"）；
4. **去重改键**：`Deduplicate` 的键去掉 `kind`（当前 25.4% 重复的直接原因）。

仍待提供的素材：化学那次的 `classnote.db`、两路转写、原始 OCR——有了这些才能把
"重复率""标注覆盖率"跑成真实数字，而不是样本上的估计。
