# CI 交付说明：build-and-test 工作流

> 对应方案最后一节"黄金样本 + CI 断言"的 CI 部分。
> 工作流文件：`.github/workflows/build-and-test.yml`

## 1. 为什么这一步值得单独做

本次交付的一半价值在那张 572 个测试的回归网里，而这张网守的是一类**特别隐蔽**的失败：
不是"功能没写"，而是"看起来对、实际改坏了"——

- `utf8` 被当成化学式改成 `utf₈`
- `C02` 的 `0` 被修成 `O` 之后又被下标逻辑吞掉
- `d_{i,j}` 因为下标转不了而被去括号成 `d_i,j`
- `\times` 命令把后面的空格一起吃掉（`a ×b`）
- `OH-` 因为首字母不是大写而被离子正则漏掉

这些都不是崩溃，是**静默的错误内容**。网不挂在流水线上，效力就打折——人总会忘记手动跑，
而"我记得上次跑过"是这类 bug 最喜欢的温床。

## 2. 工作流做了什么

| 步骤 | 内容 | 为什么这么设计 |
|---|---|---|
| 触发 | push 到 `main`、向 `main` 提 PR、手动 `workflow_dispatch` | 只改 `docs/**` 或 `*.md` 时不跑（省额度，也不制造噪声） |
| 运行环境 | `windows-latest` | **必须是 Windows**：主项目是 WPF（`net8.0-windows10.0.19041.0`），测试项目引用它，ubuntu 上连编译都过不去 |
| 缓存 | `~/.nuget/packages`，键绑定两个 csproj 的 hash | 本项目依赖较重（ONNX Runtime、WebView2、QuestPDF、SQLite），冷启动 restore 要几分钟 |
| 构建 | **Release**（而非 Debug） | 与发布构建同一套优化设置，避免"Debug 过、Release 挂" |
| **清点测试数量** | `--list-tests`，若 < 500 直接失败 | 防"空跑"：若某次重构把测试文件漏出编译范围，会得到一套**绿色但没验证**的流水线——比不跑更危险 |
| 跑测试 | `--logger trx`，产物上传为 artifact（保留 14 天） | 失败时能下载原始报告定位 |
| 汇总 | 把通过/失败数与**失败用例名**写进 Actions 页面 | 不必点进日志翻找 |

## 3. 本地完整验证过（不靠"推上去看看红不红"）

推之前我把工作流**拆出来在本地实跑了一遍**，因为 CI 脚本"看起来对"和"实际对"之间
差着一次幂等性、一次路径大小写、一次退出码：

| 验证项 | 做法 | 结果 |
|---|---|---|
| YAML 合法性 | PyYAML 解析 | ✅ 通过（`on` 被解析成布尔键属正常，GitHub 自己的解析器认得） |
| PowerShell 语法 | 把 5 个 `run` 块抽出，逐个喂给 PowerShell AST 解析器 | ✅ 全部 OK |
| 清点步骤 | 实跑 `step5.ps1` | ✅ 报"发现 572 个测试"、退出码 0 |
| 清点步骤的**顺序依赖** | 先删 Release 产物再跑 | ✅ 如实失败并给出可操作报错（"测试数量异常偏少…"），说明它真的能拦住空跑 |
| 跑测试步骤 | 实跑 `step6.ps1` | ✅ 572 通过 |
| 汇总步骤（绿） | 实跑 `step7.ps1` | ✅ 生成 `## ✅ 测试结果` 表格 |
| **汇总步骤（红）** | 故意改坏一个断言 → 跑 → 还原 | ✅ 生成 `## ❌ 测试结果` 并列出失败用例名 |

红路径那条尤其重要：CI 的价值在失败时才能体现，而"失败时脚本自己先崩了"是最常见的坑。

## 4. 已知的一条噪声

`IncrementalTranscriptionDisposeTests.Dispose_IsIdempotent_AndSignalsInputComplete`
是**计时脆弱**的（验证增量转写线程的退出时机，满负载跑整套时会超时；
单独跑或全量重跑均通过）。它在本地出现过一次，与本次改动无关。

如果它在 CI 上偶发变红，**不要**去放宽断言——那是把真问题埋掉。正确做法是给
`workflow_dispatch` 手动重跑一次确认真伪，然后单独治这个测试（例如把固定等待换成条件轮询）。
现在它被保留在工作流里，就是为了让这件事**看得见**。
