# 该修 OCR 还是修提示词？——结论与落地方案

> **✅ 已实施（2026-09-14）**：P0 的两条主线都已落地——
> ① 客户端新增可选的**内网 PaddleOCR 服务**（`OcrEngineConfig` / `PaddleOcrService` / `OcrServiceFactory`，含失败回退与冷却）；
> ② 素材层的**确定性降噪** `OcrTextNormalizer`（实测 OCR 体积 −35.6%）；
> ③ 提示词补了"OCR 不清"兜底口径与 OCR 条目 source 规则。
> 部署与设置见 [OCR 服务设置与部署](OCR-服务设置与部署.md)，本文保留当时的判断依据。
> P1（公式行标记、误识替换表扩充）与 P2（换引擎）仍待做。

**结论：主要修 OCR（素材层、确定性），提示词只补两条兜底规则。两者不是二选一，但主次不能颠倒。**

理由一句话：**字符级噪声是代码能确定性解决的，模型（尤其是小模型）做不了也不该做符号纠错。**
本轮两个样本正好各自证明了这一点（一个把 `+1` 修丢，一个时对时错地"顺"乱了公式约束）。

## 一、先看证据：噪声到底有多大、是哪一类

以这条记录为例（该记录 75 张截图的 OCR 原文属本机真实数据，**未随仓库发布**）：

| 指标 | 数值 | 含义 |
| --- | --- | --- |
| OCR 正文字符数 | 18134 | — |
| 去掉所有空白后 | 9885 | **空白占 45.5%**：全是 Windows OCR 在 CJK 之间插的空格 |
| 逐字被空格拆开的行 | 359 / 825 行 | 近一半的行是"用 f （ n ） 代表 凑 出"这种形态 |
| 误识字符 `主` | 47 次 | 几乎全是 `m 主 n`（应为 `min`） |
| 误识字符 `巨` | 22 次 | `f 巨 一 1 ]`（应为 `f[i-1]`） |
| `丿` / `刂` | 各 3 次 | `（ 0 丿 < i, 可 刀 < a[i])` 里的比较号/下标 |

**这些全是"字符级"问题，规则能修。** 而 45.5% 的空白本身就是白烧的 prefill：
第 3 段 OCR 7167 字里约 3200 字是空格，模型要用这些 token 去"猜"哪两个字符原本连在一起。

## 二、为什么不该把这件事交给提示词

提示词现在要求"技术内容逐字照抄原文"。而**原文（OCR）本身就是错的**，模型只有两种下场：

| 样本 | 面对 `f(n)=min(f(n-I)TI,f(n-5)+I,f(n-II)+I)` 的表现 |
| --- | --- |
| 样本 1（第 1 段） | 把 `+I` 修成 `+1` 两处，却把 `f(n-I)TI` 修成 `f(n-1)`，**丢掉一个 `+1` → 公式变成错的** |
| 样本 2（第 3 段） | `m 主 n` 原样抄进笔记（整段不可读）；`（0 丿 < i, 可 刀 < a[i])` 被"顺"成 `（0 < i, j < a[i]）` —— 看起来合理，**含义是错的** |

也就是说：**让模型猜 OCR 乱码 = 把随机性塞进产品的核心正确性里。** 大模型偶尔能猜对，
小模型只会时对时错；而"错得看起来合理"的公式比乱码更危险（用户不会去核对）。

## 三、分工：谁修什么

### A. OCR / 素材层（代码，确定性，可单测）—— 主战场

| 项 | 做法 | 收益 |
| --- | --- | --- |
| ① CJK 逐字空格合并 | 只在**两侧都是 CJK**、或**CJK 与全角标点**之间删空格 | 立刻砍掉 ~45% 的 OCR 体积，模型能看清行的结构 |
| ② 全角/半角统一 | `（）`→`()`、`，`→`,`（正文标点保留中文习惯需权衡） | 公式与代码可被正确识别 |
| ③ 重复幻灯片折叠 | **已有**：`NoteSegmenter.CollapseDuplicateOcr`（仅折叠归一化后完全相同的相邻条目） | 已经省掉大量重复 |
| ④ 公式行识别与标记 | 命中公式特征（`min(`/`max(`/`f(`/`[`/`=`）的行，包成 `$$…$$` 或加 `[公式]` 前缀 | 让模型知道"这行是公式"，也让笔记渲染直接可用 |
| ⑤ 高频误识保守替换表 | 仅在高置信上下文替换：`m 主 n`→`min`、`巨`→`]`、`丿`/`刂`→`<`、`刂`→`<`；不确定不动 | 修掉最常见的十几类噪声 |

⚠️ **一个必须避开的坑：不能无脑去空格。** 这条记录的 LIS 样例是
`输入：7 / 1 7 3 5 9 4 8 / 输出：4`——直接把空白全删会变成 `1735948`，语义当场毁掉。
所以合并规则必须限定为"CJK↔CJK / CJK↔全角标点"，**ASCII 数字与字母之间的空格要保留**。

**落地位置建议**：写成纯函数放在 `ClassNote\Services\` 下（与 `NoteSegmenter` 同级，便于单测），
在**素材装配时**调用（`NoteProcessor.BuildOcrMaterialAsync` / `NoteSegmenter.ParseOcrEntries` 之前），
**不要改写数据库里的 OCR 原文**——这样：
- 已有的 75 条记录**不用重新 OCR**，下次生成笔记就自动受益；
- 原始 OCR 仍留在库里可追溯，出问题能对拍。

### B. 提示词层（只补两条，不承担纠错）—— 辅助

1. **残余噪声的兜底口径**（现在的提示词没有，所以模型只能瞎抄或瞎猜）：
   > 遇到 OCR 文本里明显断开、错乱的字符：能按上下文确定含义的，整理成正常写法；
   > **确定不了的，原样保留并在该处标注「OCR 不清」**，禁止猜一个"看起来合理"的符号。
2. **OCR 条目的 `source` 规则**（现在模型只能自己猜，样本 2 就猜错了一条）：
   > 【课件/板书截图 OCR】里的内容，`source` 一律填「课件」；能确认是教室现场板书才填「现场」；
   > 判断不了留空字符串。

### C. 不要交给模型的事

- 把 `m 主 n` 还原成 `min`、把 `0 丿 < i` 还原成正确的下标约束——**这类还原交给代码或标注，不交给模型**。
- 判断"这个公式是不是老师反复强调的重点"这类语义判断，仍然留给模型（这是它的强项）。

## 四、执行顺序与验收

| 优先级 | 动作 | 验收方式 |
| --- | --- | --- |
| **P0** | OCR 规范化（① + ②）+ 提示词两条规则 | 同一份素材、同一个模型跑前后对拍：统计「乱码字符数」「公式条数正确率」「OCR 素材字数」 |
| P1 | ④ 公式行标记 + ⑤ 误识替换表 | 抽查 20 行公式，人工判定还原正确率 |
| P2（可选） | 换 OCR 引擎（RapidOCR/PaddleOCR）或引入公式识别 | 先看 P0/P1 后还剩多少噪声，再决定值不值得动 |

**P0 的预期**：OCR 素材 20373 字 → 约 11–12k 字（空白占 45%），第 3 段 7167 → 约 4k；
模型不用再把一半算力花在"猜空格"，公式乱码条数应显著下降。

## 五、一句话回答

> **先修 OCR（素材层的确定性规范化），提示词只补"判断不了就原样保留并标注 + OCR 条目来源一律填课件"这两句。
> 把符号纠错留给模型，等于把产品正确性交给运气。**
