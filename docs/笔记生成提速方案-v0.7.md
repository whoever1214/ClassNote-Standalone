# 笔记生成提速方案（v0.7 候选）

> 目标：把「下课点结束 → 能读到笔记」从**十几到几十分钟**压到**分钟级**，并且**不牺牲笔记质量、不改变转写文本**。
> 本文只做方案，不含已实施的代码改动。所有收益估算都标了口径与出处，未实测的一律标注「待测」，不虚报。

## 0. 现状：时间花在哪（带证据）

### 0.1 课后管线是严格串行的三段

`ClassNote/Services/NoteProcessor.cs:46-147`：

```
点「结束」→ [STT 逐路串行] → [OCR 逐张串行] → [LLM 分段串行 → 合并] → 落库 completed
```

三段之间**没有任何并行**：OCR 要等 STT 全部跑完（`:56` 之后才 `:65` 循环），LLM 要等 OCR 全部跑完（`:110`）。
而 OCR 与 STT 之间、STT 与录音之间其实没有数据依赖——这是当前最大的一处浪费。

### 0.2 决定性瓶颈：STT 是「录音时长 × 0.29 × 路数」，而且全在课后

已有基线（`TestResults/bench/performance-report.md:48-52`，4 核 Xeon E-2124 / 3.3GHz）：

| 指标 | 实测值 | 出处 |
|---|---|---|
| STT 温调用耗时 | 4.68s / 15.94s 音频 | `performance-report.md:48` |
| **实时因子 RTF** | **≈ 0.29** | `performance-report.md:49` |
| 模型加载 | ≈ 6.05s（真机冷盘场景实测 **≈33s**） | `performance-report.md:48`；`TestResults/reports/full-chain-test-report.md:21` |
| 单实例内存增量 | ≈ 594 MB | `performance-report.md:50` |

于是：

| 场景 | STT 耗时（按 RTF 0.29 外推） |
|---|---|
| 45 min 课 · 单路 | ≈ 13 min |
| 45 min 课 · **双路**（v0.6.0 默认推荐的「麦克风和系统声音」） | ≈ **26 min** |
| 90 min 课 · 双路 | ≈ **53 min** |

> ⚠️ 这里有一个 v0.6.0 引入的**用户可感知回退**：分轨录音改成「两路分开各转写一遍」（`NoteProcessor.cs:158-190` 的 `foreach` 串行），
> 换来「现场/课件」的来源标注能力，代价是**课后等待时长直接翻倍**。README:39 也自认「处理时间约翻倍」。
> 这不是 bug，但它让「更快产出笔记」这件事从优化项变成了必修项。

### 0.3 现存的其它固定损耗

| # | 损耗 | 位置 | 量级 |
|---|---|---|---|
| 1 | 每个录音会话 `new SenseVoiceSttService()`，模型重载一次 | `RecordingViewModel.cs:41-42` | 每次 **6–33s** |
| 2 | ORT `InferenceSession` 跨实例不释放，内存累积 | `SenseVoiceSttService.cs:170`；bench BT-1 | 3 会话 **1.8 GB**（单实例仅 ~0.7 GB） |
| 3 | 停录路径 awaited 阻塞：复制音频（90min 单路 172 MB / 双路 344 MB）+ 刷新队列 + 结束会话 | `RecordingViewModel.cs:248,285,298` | 点「结束」到「已停止」**1–10s** |
| 4 | LLM 分段**串行**（每段一次往返 + 最多 8192 输出 token） | `LlmService.cs:121-162`；`NotePromptBuilder.cs:69` | 4–8 段 × 30–60s ≈ **2–5 min** |
| 5 | 合并阶段再串行跑 1–3 轮 | `LlmService.cs:226-255` | +30–90s |
| 6 | 每次 LLM 调用 `new HttpClient`（新建连接池 = 重新 TCP+TLS 握手） | `LlmService.cs:465`（另 `:292,:328`） | 每次 100–300ms |
| 7 | OCR 逐张串行，且全部堆在 STT 之后 | `NoteProcessor.cs:65-86` | 100 张 ≈ 11s（本机 107ms/张），4K/慢机 30–60s |
| 8 | fbank 每帧 3 次托管分配 + 稠密 mel 卷积（80×257 乘加/帧，其中绝大多数是 0） | `FbankExtractor.cs:124,134,145,152` | 90min ≈ 54 万帧 ≈ **160 万次分配**，估 1–3 min（待测） |
| 9 | 主页 3s 轮询常开 | `MainPage.xaml.cs:41-42`；bench BT-3 | 恒定 CPU 浪费，处理期与入库争用 |

**结论：只要 STT 还留在课后，其他优化都是零头。** 优化主轴是「把 STT 和 OCR 从课后的等待窗口，搬进课堂上本来就在流逝的 45/90 分钟里」。

## 2. 核心思路：把「课后串行等待」改成「课上并行流水线」

```
现在：  [========== 录音 90min（CPU 空闲）==========] → [STT 53min] → [OCR 1min] → [LLM 4min] → 可读
                                                              ↑ 用户就等在这里

改后：  [== 录音 90min：后台 STT 分块推进（26min CPU / 2 路并行）+ OCR 随截图即做 ==] → [尾块+合并 2min] → 可读
                                                                                        ↑ 用户几乎不用等
```

关键判断：**这不是让机器多干活，而是把同样的计算量挪到机器空闲的时间段，总能耗基本不变**（同样的 CPU-seconds，只是发生在课堂上而不是课后）。
因此「电池续航」不构成反对理由；真正要管的是**课堂期间的资源占用上限**（§4 风险与限流）。

## 3. 优化清单（按收益/成本排序）

### P0-1 边录边转写（增量分块 STT）— 收益最大

**做法**
1. 在 `AudioService.CaptureChannel.SamplesProduced` 上挂一个**非阻塞 tap**（PCM16 / 16kHz / mono）。
   现有单路直写路径已在采集线程上同步分发（`AudioService.cs:792-805`，类注释 `:762-772` 明确要求订阅方「必须立即返回」），
   双路 `DualTrackRecorder` 的 per-channel handler 同理（`:848-861`）→ tap 只能写入**有界队列**，队满丢帧并计数告警，**绝不阻塞采集线程**。
2. 新增 `StreamingSttSession`：按 **30s** 对齐切块（与现有 `ChunkSeconds = 30` 一致，`SenseVoiceSttService.cs:22`），
   后台单 worker 顺序消费「fbank → LFR → RunInference → Clean」，结果按 `(sessionId, track, chunkIndex)` 落库。
3. 结束时只补算**尾部不足一块**的部分 + 任何失败/未完成块。

**为什么这样切**：分块边界与现有批处理完全相同 ⇒ 转写结果可做到**逐字节一致**，质量零风险（§5.1 有回归对拍）。
同时天然获得两个附带能力：**断点续跑**（今天 STT 跑到 40 分钟崩了，整条音轨全废）与**只重试失败块**。

**收益**：90min 双路 53 min → 课后 0（尾块 ≤30s）；45min 单路 13 min → 0。

### P0-2 双路并行转写

`NoteProcessor.cs:164` 的 `foreach` 改 `Task.WhenAll`，两路 worker 并行。
ORT CPU 会话的 `Run` 是线程安全的，但默认 `intra_op = 全部物理核`，并发跑会互相抢核 → 需要配 `intra_op_num_threads = max(1, cores/2)` 再并发。
**待测**：单会话并发 vs 两会话（内存 2×600MB，不推荐）vs 维持串行，取实测最优。

**收益**：双路场景 2×（在 P0-1 之后这条只影响「兜底批处理路径」和「课堂期间占用上限」，仍值得做）。

### P0-3 STT 模型常驻单例 + 提前预热

- `new SenseVoiceSttService()`（`RecordingViewModel.cs:41-42`）改为进程级单例（`Lazy<T>`），会话间复用 `InferenceSession`。
- **开始录音时就预热**：课堂期间有大把空闲，把 6–33s 的加载挪到「用户点开始录音」之后的后台线程。
- 修 bench BT-1 的内存累积：`SessionOptions.EnableCpuMemArena = false`（**待测**其对 RTF 的影响）或至少在会话结束后释放 arena。

**收益**：每次会话 −6~33s；多会话进程内存 1.8 GB → ~0.7 GB。

### P0-4 停录路径不再阻塞

`StopRecordingCoreAsync`（`RecordingViewModel.cs:262-300`）里 awaited 的
音频复制（`UploadAudioTracksAsync`，`UploadService.cs:73-105`）→ 移到后台任务，与管线并行；
`FlushQueueAsync` / `FlushAudioQueueAsync`（当前是 `Task.CompletedTask` 空实现）与 `EndSessionAsync` 一并移出 UI 关键路径。
管线**直接读 `%TEMP%` 的原始 WAV**，复制与转写读同一文件（只读共享，无冲突）。

**收益**：指标 C 1–10s → <300ms。

### P1-1 分段 LLM 并行（有界并发）

`LlmService.cs:121-162` 顺序 for 改 `SemaphoreSlim(3~4)` 并发；`MergeCascadeAsync` 的组间合并同理。
注意：现有 `ChatAsync` 的退避重试是**每调用独立**（`maxAttempts = 3`，`:469`），并发后必须加**跨任务共享的自适应限流**
（遇 429/5xx 全局降并发 + 退避），否则会自己把自己的速率打爆。

**收益**：分段阶段 3–4×，省 2–4 min（P1-4 未开时这是课后等待的主要残项）。

### P1-2 HttpClient 复用

`LlmService.cs:465` 每次 `new HttpClient` ⇒ 每次新建连接池 ⇒ 每次重新 TCP+TLS 握手。
改静态 `HttpClient` + `SocketsHttpHandler`（`PooledConnectionLifetime = 5min`），
**请求级超时**改用 `CancellationTokenSource.CreateLinkedTokenSource(...).CancelAfter(timeout)`（`HttpClient.Timeout` 是 client 级的，不能再用）。

**收益**：每次调用 −100~300ms；5 次调用 ≈ 1s。国内直连 `api.deepseek.com` 时握手成本更明显。

### P1-3 稳定前缀吃满上下文缓存

把**可变内容全部留在 user 消息**，system prompt（`NotePromptBuilder.cs:15,27,36`）严格保持不变：
当前 `NoteSystemPrompt` / `SegmentSystemPrompt` 是常量，已达要求；**约束是今后不许往 system 里插课程名/时间戳**。
DeepSeek 对相同前缀自动命中缓存 → 缓存部分按低价计费、prefill 更快。

**收益**：首 token 更快、成本下降。**待测**（需实测命中率与延迟差）。

### P1-4 边录边整形（可选，默认关）

转写块一就绪就触发对应分段的 LLM 调用 → 下课时只剩尾段 + 合并。
**收益**：A 指标从 ~2–3 min 进一步压到 **~60–90s**。
**门槛**：课堂上就要联网并产生 API 费用；若用户中途删除录音，这部分花费已经发生。
→ 建议：**默认关**，设置里给开关；「课表自动录音」场景（无人盯着）可默认开。

### P1-5 流式输出 + 增量落库 + 边生成边显示

- `ChatAsync` 支持 `stream: true`（SSE 解析），分段完成即写草稿笔记（新增 `note.status = generating`），合并完成后覆盖为终稿。
- 笔记页（`NoteViewPage` / `NoteViewModel`）在 generating 状态下周期刷新（或事件驱动）。
- 兜底顺序天然友好：先 `AssembleNote` 机械装配让用户**立刻可读**，再用 LLM 合并结果覆盖（`LlmService.cs:181` 已有 `AssembleNote` 可复用）。

**收益**：指标 D 从「生成完成后才有」→ **<10s 见到第一批知识点**。

### P2-1 OCR 与 STT 并行，并随截图即时做

- 截图落库后（`RecordingViewModel.cs:341-353`）立刻在后台线程 OCR，结果写入 `screenshots.ocr`；
  管线阶段（`NoteProcessor.cs:65-86`）只读现成结果。
- WinRT OCR 与 ORT 推理走不同的执行资源，天然适合并行。
- **顺带做 OCR 文本去重**：同一张幻灯片反复截屏会产生大量近乎相同的文本（`ScreenshotService.cs:40` 每 10s 一帧，
  仅在 pHash 变化时才保留，但批注过程中的重复仍不少），用文本指纹/相似度合并，**同时缩短 LLM 输入** ⇒ prefill 更快、token 更省。

**收益**：课后 OCR 段 10–60s → 0；LLM 输入变短带来的额外收益待测。

### P2-2 fbank 与解码热点优化

`FbankExtractor.ComputeFbank` 每帧分配 `Complex[512]` + `double[257]` + `float[80]`（`:124,134,145,152`），
mel 滤波器稠密卷积 80×257 次乘加/帧（`:157-158`）。

- 稀疏三角滤波器（只遍历非零 bin）：mel 计算量约 −90%
- 复用行缓冲、消除每帧分配：GC 压力大幅下降
- `Parallel.For` 按帧并行 fbank（embarrassingly parallel）

**收益（估）**：fbank 占比从 ~10–20% 降到 ~3–5%，90min 场景省 1–3 min。**待测**。
**硬约束**：输出特征必须与现有实现一致 → 以位一致回归（§5.1）作为门槛，否则不许合入。

### P2-3 VAD 静音跳过（收益大、风险中等）

课堂里有大量静音/噪声（自习、课间、只写板书不讲话）。保守能量 VAD + 连续静音 ≥1.5s 才跳过，
静音段不送推理但**保留时间轴占位**，避免破坏分段与时间提示。

**收益**：实际语音占比 50–70% ⇒ 省 **30–50% 推理时间**。
**风险**：漏掉轻声讲解 = 内容永久丢失。→ 阈值取保守值，灰度期用同一素材做「开/关 VAD 的转写文本 diff」A/B，diff 超出预期即回滚。

## 5. 验收与测量

### 5.1 正确性门槛（先于性能门槛）

1. **转写位一致**：同一 WAV，批处理 vs 增量分块，输出文本 `==`（含标点与空格拼接方式）。
2. **fbank 位一致**：如做 P2-2，特征张量逐元素相等（`devtools` 现有素材可复用）。
3. **失败语义不回退**：单块失败只影响该块；单路失败不影响另一路；素材全空仍不调用 LLM（`NoteProcessor.cs:92-97` 的既有约定必须保留）。
4. 现有 19 个测试文件（`ClassNote.Tests/`）全绿，并新增：
   `StreamingSttSessionTests`（分块边界/拼接/失败块重试/tap 丢帧计数）、`LlmConcurrencyTests`（并发上限与限流）。

### 5.2 基线测量工具

新增 `devtools/NoteBench`（与既有 `AudioProbe` / `RenderHarness` 同风格）：
输入 WAV（单/双路）+ 截图目录，按阶段打点输出 JSON，纳入 `TestResults/bench/` 的既有报告口径。

**固定场景**（每次优化前后各跑一遍，同机同素材）：

| 场景 | 素材 | 关注指标 |
|---|---|---|
| S1 | 45 min 单路 | STT / OCR / LLM 分段 / 合并 各段耗时 |
| S2 | 45 min 双路 | 同上 + 两路并行度、峰值内存 |
| S3 | 90 min 双路 + 60 张截图 | 端到端 A 指标、峰值内存、课堂期间 CPU 占用 |

### 5.3 用户可见的进度

- 录音页：`已转写 12/45 分钟`（增量进度，不再只有「转写中…」）
- 主页会话状态细分：`转写中 / 整理中 / 完成`（现在只有一个笼统的 processing）
- 笔记就绪时发**托盘气泡**（应用已有托盘常驻，改动小、感知收益大）
- 主页 3s 轮询改为「只在确有 pending 时开启」（顺带修 bench BT-3 的恒定 CPU 浪费）
